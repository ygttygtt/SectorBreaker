# 简历原文与项目事实对齐

## 简历中的项目定位

简历将项目描述为：

> SectorBreaker 领域破壁｜高自治 Multi-Agent 领域研究与知识库管理系统。

核心角色是“核心开发 / Agent 架构设计”，技术栈写的是：

```text
Python, Custom Agent Kernel, FastAPI, React, TypeScript,
Pydantic, SQLite/FTS, RAG
```

项目简介强调以下能力：

- 面向陌生领域研究和长期知识维护；
- Master Agent 是决策核心；
- 动态调度审计、研究、验证、知识编辑等 Specialist Agent；
- 支持资料导入、知识缺口发现、检索研究、证据验证、知识修改、审批应用和版本回滚；
- 输出带来源引用、可持续更新、可直接导入 Obsidian 的领域知识库；
- 支持持续追问、补充资料和维护目标；
- 恢复既有 Agent State 和知识版本；
- 新增知识可以沉淀为知识卡片，已有笔记通过 Diff 和审批后更新；
- 保留证据、版本差异和回滚记录。

## 简历职责逐条映射

### 1. Master Agent 自主决策

简历表述：Master Agent 根据当前知识、任务进度和工具执行结果，决定继续检索、调用专家、生成知识、向用户追问或结束任务。

仓库实现：

- `LLMAgentPolicy.decide()` 把当前 State、Tool Schema、Artifact Memory 和最近 Trace 交给 LLM，返回强类型 `AgentDecision`。
- `AgentKernelRuntime.run()` 循环执行 Decide -> Act -> Observe -> State Update -> Re-decide。
- `AgentActionType` 支持 `call_tool`、`update_state`、`write_artifact`、`review_artifact`、`ask_user`、`finish`、`block`。
- Runtime 不按照 L1-L5 自动顺序推进；知识层只是 State 中的认知结构。

面试重点：自主性来自“下一步由模型基于变化后的 State 决定”，不是来自项目里出现了 Agent、ReAct 等名词。

### 2. Multi-Agent 动态协作

简历表述：围绕知识库审计、资料研究、事实验证和内容编辑设计不同 Specialist Agent，由 Master Agent 按实际知识缺口按需调度。

仓库实现：

- 注册角色：`vault_auditor`、`researcher`、`verifier`、`knowledge_editor`。
- 一次最多委派四个相互独立的 Specialist 任务，通过 `asyncio.gather` 并发执行。
- 每个角色有不同工具白名单。
- Specialist 只返回 `SpecialistResult`、Finding、Tool Recommendation 或 Change Suggestion。
- Specialist 不能直接写文件，也不能应用 ChangeSet。

必须诚实说明：当前 Specialist 是“动态委派 + 强类型结果 + 并发分析”，还不是每个 Specialist 都拥有独立多轮 ReAct 工具循环。外部搜索建议仍回到 Master 调度器执行。

### 3. State 管理和中断恢复

简历表述：持续保存项目目标、已有知识、研究证据、待解决问题和历史执行结果，使 Agent 能在中断或后续对话中恢复进度。

仓库实现：

- `SectorBreakerState` 保存 MetaContext、KnowledgeSchema、SharedKnowledge、EvidenceRefs、WorkingMemory、DecisionLog、ArtifactMemory、维护任务、AutonomyPolicy、BudgetUsage 和 HumanFeedback。
- 每次成功写入 Artifact 后保存 `artifact_write` checkpoint。
- 结束时保存 `run_end_completed`、`run_end_partial` 或诊断型 `run_end` checkpoint。
- `/resume` 恢复同一个 `waiting_for_human` run；预算不会重置。
- `/recover` 为意外中断 run 创建带 `resumed_from_run_id` 的恢复子 run。
- Lease Owner 和 Lease Expiry 防止旧 Worker 在失去所有权后继续写事件或完成运行。

### 4. 证据和安全机制

简历表述：研究结论关联来源和验证状态；证据不足或冲突时交由 Verifier 继续核查；修改已有笔记先生成 Diff，再审核写入，并保留历史版本。

仓库实现：

- Evidence 保存 URL、正文摘录、摘要、来源质量、验证状态、冲突和反证字段。
- `verified` Claim 没有真实项目 Evidence 时会被 Reducer 降级。
- ChangeSet factual change 在 apply 边界必须携带项目内真实 Evidence ID。
- `base_hash` 不一致时进入 `conflicted`，不会覆盖新版本。
- Artifact Revision 不可变，旧版本标记 inactive 并建立 supersedes 链。
- Rollback 生成恢复 revision 或撤销新建 Artifact。

### 5. 持续维护

简历表述：优先从已有知识库寻找答案，无法覆盖的问题进入研究和维护流程，验证后成为新卡片或原笔记补充。

仓库实现：

- Chat 和 Agent 共用 `ProjectRetriever`。
- Follow-up 会检索 Evidence、Document Segment 和 Active Artifact。
- 相同规范化问题重复追问时复用现有 Follow-up Artifact，避免重复建页。
- Existing Vault 通过确定性审计生成持久化 Maintenance Backlog。
- Agent 可以选择维护任务、研究缺口并提出 ChangeSet。

## 简历没有展开但面试可讲的实现亮点

- SearchProvider、ContentExtractionProvider、EmbeddingProvider、LLMProvider 都通过接口隔离。
- 搜索支持 Tavily、Serper、Brave、Exa、Firecrawl，`multi` 模式并发执行并轮询公平合并。
- 生产搜索对返回 URL 再做域名策略校验，不能只相信搜索厂商的 domain 参数。
- URL 抽取有 SSRF 基线防护，拒绝 localhost、私网、保留地址和带凭证 URL。
- 本地 Hybrid RAG 使用 `BAAI/bge-small-zh-v1.5`、增量 SQLite 向量索引和 RRF。
- 向量模型失败时明确返回 `lexical_degraded`，不会伪装成 Hybrid。
- Runtime 对 Search Tool、真实 Provider Fan-out、正文抽取和 Writer 分别计费。
- 当前真实验收曾产生 42 条搜索 Evidence、4 个 Active V3 Artifact，并完整跑通 ChangeSet 审批、应用、同 Run 恢复和导出。

## 关于简历技术栈的边界

- SectorBreaker 当前不是 pgvector 架构。它使用 SQLite FTS + SQLite 中的本地向量索引。
- SectorBreaker 当前没有 Cross-Encoder Reranker。RRF 是已实现能力，Cross-Encoder 属于个人通用 RAG 能力或其他项目经历，面试时不要混写。
- SectorBreaker 依赖中包含 LangGraph，但当前生产核心应描述为 Custom Agent Kernel，不应说成 LangGraph 固定状态图。
- 产品已上线，后端在阿里云服务器；但仓库没有公开多租户、高并发、Kubernetes 等实现，不要自行扩展。
