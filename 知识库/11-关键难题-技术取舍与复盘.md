# 关键难题、技术取舍与复盘

## 难题一：看起来像 Agent，实际是固定 Workflow

### 现象

- 代码出现 Master Agent、ReAct、State、L1-L5；
- 真实运行仍然按 L1 -> L5；
- 每层搜一两次就写作；
- UI 节点和后端执行不一致。

### 根因

新 Agent 代码和旧 Workflow 并存于生产 Namespace，开发者容易继续修补旧路径。架构中心没有真正切换。

### 解决

- 生产 Owner 收敛到一个 Agent Kernel 入口；
- 旧代码移出生产 Import；
- L1-L5 只保留为 State 中的认知 Schema；
- 前端 Workflow Definition 以后端真实定义为准；
- Version Isolation Script 扫描 Legacy Marker。

### 教训

架构重写不能只增加 Guard，必须隔离或删除旧执行脊柱。

## 难题二：LLM 长 Markdown 与 Structured Output 冲突

### 现象

Writer 想生成长 Markdown，但走了 JSON Structured Parsing，OpenAI-compatible Provider 返回 Markdown 或 SSE 包装后触发 JSONDecodeError。

### 解决

- `complete_structured()` 只用于 Decision、StateDelta、Specialist Result；
- `complete()` 用于 Markdown Plain Text；
- Writer 分节生成并发 Heartbeat；
- Provider 兼容非流式和 SSE/Keepalive 包装；
- 失败后不保存模板。

### 教训

结构化输出适合控制面，不适合所有内容生成。不要为了统一接口强迫长文本变成 JSON。

## 难题三：Fallback 模板制造假成功

### 现象

LLM 写作失败后保存结构完整但内容空洞的 Markdown，API 显示成功，用户打开文件才发现不可用。

### 解决

- 定义 `_usable_markdown` 质量门；
- 写作失败重试并记录错误；
- 不持久化 Fake Artifact；
- 连续失败停止；
- 有部分真实 Artifact 时允许 Partial Success，但必须显示 Failed Writes；
- 无 Artifact 时整个 Run 失败。

### 教训

Agent 产品的成功标准是用户拿到有用产物，不是 Python Function 返回了一个对象。

## 难题四：历史 Artifact 造成假 Finish

### 现象

Continuation Run 加载旧 Artifact 后，Agent 立刻 Finish，虽然本轮任务没有任何推进。

### 解决

Runtime 保存 `initial_artifact_ids`，完成门只接受新 Artifact，或同 Run ID 已持久化的 Artifact。

### 教训

恢复历史上下文和证明本轮完成是两件事，不能混为一谈。

## 难题五：Checkpoint 和 Artifact 不一致

### 风险

Checkpoint 保存成功，Artifact 保存失败，恢复后 State 引用不存在的文档。

### 解决

- Artifact-first；
- 每次写作后 Checkpoint；
- Run End 做幂等 Artifact 持久化；
- 持久化失败不吞异常。

## 难题六：多 Provider 搜索预算失真

### 风险

一个 Tool Call 在 Multi 模式发出多个 HTTP 请求。如果只扣 1 次，成本和风控失真。

### 解决

- Search Tool Call、Provider Request、Extraction Request 分开计数；
- Provider 返回 Typed Outcome 和真实 Request Count；
- 聚合异常保守扣费；
- 同 Run Resume 继续使用旧预算。

## 难题七：搜索厂商不一定遵守域名限制

### 风险

Provider 的 Domain 参数可能只是搜索语法提示，返回内容仍可能越界。

### 解决

- Project 级 Source Preferences 持久化；
- Require 是硬 Allowlist；
- 返回 URL 在本地再做 Canonical Host Check；
- Evidence 保存 Effective Domain Policy 和 Fallback 信息。

## 难题八：向量索引增量更新和失败安全

### 风险

- 每次 Query 都全量 Embedding，成本高；
- Force Rebuild 失败把旧索引删光；
- Metadata 变化不值得重新 Embedding；
- Superseded Artifact 仍被召回。

### 解决

- Content Hash 增量；
- Metadata-only Update 复用 Vector；
- Transactional Snapshot Publish；
- 失败回滚旧 Snapshot；
- Stale/Superseded Chunk 删除；
- Project/Provider/Model 级 Lock 防止并发重复 Embedding。

## 难题九：人工等待和 Worker 崩溃不能用一个恢复逻辑

### 区分

- 人工等待是正常业务状态；
- Worker Lease 过期是基础设施异常。

### 解决

- Waiting 使用同 Run Resume；
- Crash 使用 Interrupted + Recovery Child；
- Orphan Without Checkpoint 直接失败；
- CAS 和唯一索引防止重复恢复。

## 难题十：Specialist 越权

### 风险

如果每个 Specialist 都能搜索、写文件和 Apply，Master Agent 就失去治理能力。

### 解决

- Role-specific Tool Allowlist；
- Typed SpecialistResult；
- Specialist 只提建议；
- Knowledge Editor 也只能 Proposed Change；
- 外部调用和 Apply 都回到 Master Runtime。

## 核心技术取舍总结

### Custom Kernel vs LangGraph 固定图

选择 Custom Kernel 是为了让决策循环、StateDelta、预算和 Finish Gate 成为显式业务语义。LangGraph 可以作为宿主或基础设施，但不能用固定节点代替 Agent 判断。

### SQLite vs PostgreSQL/pgvector

选择 SQLite 是匹配 Local-first/Private-first 和当前并发模型。未来多租户再迁移，不提前支付分布式复杂度。

### RRF vs Raw Score Mixing

选择 RRF 是因为 BM25/词项分数与 Cosine Similarity 量纲不同，Rank Fusion 更稳定、解释更清晰。

### Immutable Revision vs In-place Update

选择不可变 Revision 是为了 Audit、Rollback、Active-only Retrieval 和冲突处理。

### Deterministic Audit vs LLM Audit

断链、路径、Hash、Front Matter 等结构事实用确定性 Scanner；事实陈旧、冲突等语义问题交给 Evidence-aware Agent。

### Safe Failure vs Template Fallback

宁可失败/部分成功，也不输出伪造成功产物。

## 面试回答：项目最大的架构教训

> 最大教训是不能把固定 Workflow 包装成 Agent。我们早期保留旧 Pipeline，又用模板兜底，导致单元测试通过但真实输出不可用。后来我做了生产 Owner 收敛和版本隔离，把执行中心改成 State + Tool + Observation + StateDelta 的 Agent Kernel，并规定真实 E2E、事件 Trace、Evidence 和导出 Markdown 才是验收标准。这个过程让我认识到 Agent 工程的难点不只是 Prompt，而是权限、状态、持久化、失败语义和真实产物质量。
