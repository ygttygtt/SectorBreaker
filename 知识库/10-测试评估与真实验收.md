# 测试、评估与真实验收

## 测试策略

SectorBreaker 的测试分四层：

1. Schema/Unit：Pydantic、Reducer、Tool、Provider、Storage。
2. Integration/API：Vault Lifecycle、Run State、SSE、RAG API。
3. Architecture Gate：Version Isolation、禁用旧 Workflow 和已退休企业路径。
4. Real Acceptance：真实 LLM、Search、Extraction、Embedding 和人工审批闭环。

## Agent Kernel 关键测试

- LLM 决定的工具顺序会真实执行；
- 多个 Tool Call 之间会更新 State；
- Unknown Tool 返回失败 Observation；
- Search 超预算被硬阻断；
- 只有历史 Artifact 时不能 Finish；
- 同 Run Resume 后的 Artifact 可以满足 Finish；
- Artifact Checkpoint 失败会向上抛出；
- Main Writer 失败后保留已经完成的 Artifact；
- Context 中包含 Artifact Memory。

## RAG 关键测试

- 无关键词重合的语义召回；
- Lexical/Vector 都参与 RRF；
- 不变 Chunk 不重复 Embedding；
- Content Change 重新 Embedding；
- Metadata Change 不重新 Embedding；
- Superseded Revision 被移出索引；
- Force Rebuild 失败保留旧 Snapshot；
- 同 Document 只保留最佳 Segment；
- Dimension Mismatch 明确 Degraded；
- Agent 和 Chat 共用 Retriever；
- 并发同步对同一 Snapshot 只 Embedding 一次。

## Knowledge Control Plane 关键测试

- Vault Import 保留嵌套路径且幂等；
- Audit 生成稳定 Backlog；
- Apply/Rollback 保留完整历史；
- Base Hash 冲突不覆盖；
- Multi-operation 冲突时零部分写入；
- Unknown/Cross-project Evidence 被 Denied；
- Superseded Revision 不参与 Retrieval/Export；
- 重启后 Revision 关系仍存在。

## Run Lifecycle 关键测试

- Migration 重启幂等；
- 只 Reconcile 过期 Lease；
- 有 Checkpoint 才能 Recover；
- Waiting Run 不被 Stale Reconciliation 误伤；
- Resume Claim 是 Compare-and-Set；
- Waiting Event 在释放 Lease 前持久化；
- 旧 Worker 不能继续 Append/Finalize；
- 一个 Interrupted Run 只能有一个 Recovery Child。

## Provider 和安全测试

- Tavily/Serper/Brave/Exa/Firecrawl 请求适配；
- Multi Provider 并发、失败隔离、去重和公平合并；
- Prefer Fallback 和 Require Hard Allowlist；
- 实际 Provider/Extraction Budget；
- 正文抽取和来源评估；
- URL Safety 拒绝非 Public Target；
- Runtime Config Atomic Write 和 Secret Preserve。

## 真实验收为什么不可替代

Fake Provider 只能证明接口和错误分支。它不能证明：

- 真 LLM 的 Decision JSON 稳定；
- Search 返回的来源有用；
- 正文抽取真的可读；
- Writer 生成的 Markdown 有内容；
- 运行十分钟时 UI/SSE 是否可观察；
- 人审后同 Run 能否恢复；
- 最终 Obsidian Vault 是否可用。

项目曾经发生过“单元测试通过，但 Writer JSONDecodeError 后保存模板 Markdown”的问题，因此真实产物检查被设为强制门禁。

## 版本隔离验收

当前生产路径禁止出现：

```text
Knowledge Builder
Document Writer
specialist_react_loop
EV-V1-
ART-V1-
已使用保底
```

也禁止已退休 Enterprise Talent/Boss Job Source 路径进入生产 Import、API、Frontend 和 Schema。

`python tools/check_version_isolation.py` 是架构门禁，不只是字符串洁癖。它防止旧执行 Owner 重新进入生产链路。

## Agent Eval 如何继续完善

当前已经有工程正确性和真实 E2E，但还需要更系统的质量指标：

- Task Success Rate；
- Useful Evidence Gain；
- Duplicate Search Rate；
- Tool Failure Recovery Rate；
- Claim Citation Precision；
- Claim-Evidence Support Accuracy；
- Conflict Detection Recall；
- Artifact Completeness/Readability；
- Human Acceptance Rate；
- Cost、Latency、Provider Failure Rate；
- Rollback/Conflict Rate。

对于 RAG，可以构建标注集计算 Recall@K、Hit Rate、MRR、NDCG 和 Citation Correctness。不要把“Top-5 全命中”这类其他项目的指标挪到 SectorBreaker。

## 面试回答：如何评估 Agent 是否真的有效

> 我把评估分成三层。第一层是 Runtime Correctness，比如工具白名单、预算、Checkpoint、Conflict 和 Evidence Gate；第二层是 Retrieval/Artifact Quality，比如 Recall@K、Citation Accuracy、内容完整性；第三层是真实业务闭环，要求使用真实 LLM 和搜索，从研究到正文抽取、写 Artifact、人工批准 ChangeSet、恢复 Run、导出并回滚全部跑通。我们曾经因为只看单元测试而放过模板产物，所以现在真实输出检查是强制门禁。
