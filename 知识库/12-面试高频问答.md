# 面试高频问答

## Q1：请介绍一下 SectorBreaker

SectorBreaker 是一套高自治 Multi-Agent 领域研究和知识库管理系统。我负责核心开发和 Agent 架构设计。它可以从陌生领域开始构建 Obsidian 知识库，也可以导入已有 Vault 做持续维护。核心是自研 Master Agent Kernel：每轮读取 State、Artifact Memory、Evidence 和工具结果，动态决定检索、搜索、委派 Specialist、写知识、提出 ChangeSet、请求人工或停止。系统用本地 Hybrid RAG 检索 Evidence、资料和 Active Artifact，用不可变 Revision、Diff、Base Hash、审批和回滚保证知识修改安全。产品已经上线，后端部署在阿里云服务器。

## Q2：为什么说它是真 Agent，不是 Workflow

判断标准不是用了什么框架，而是下一步是否由模型基于变化后的 State 动态决定。SectorBreaker 的 Runtime 每轮把 ContextPack、可用 Tool Schema 和最近 Observation 给 LLM，LLM 返回强类型 AgentDecision；工具结果通过 StateDelta 进入 Reducer，再触发下一轮。它可以改变搜索方向、委派不同角色、写作、追问、Block 或 Finish。L1-L5 只是认知 Schema，不是硬编码节点顺序。

## Q3：ReAct 是怎么实现的

`LLMAgentPolicy.decide()` 是 Reason/Decide，Tool Registry Dispatch 是 Act，`KernelObservation` 是 Observe，`apply_state_delta()` 是 Update。Runtime 循环直到 Finish、Waiting、Blocked、Failure 或 Max Iterations。所有动作和观察都会转成 Trace Event 和 SSE Event。

## Q4：为什么自研 Kernel，不直接用 LangGraph

项目早期用固定图时曾经出现“图很丰富但 Agent 并不自主”的问题。我希望把 Decision、Tool Schema、StateDelta、Budget、Finish Gate 和 Failure Semantics 做成显式业务契约。LangGraph 可以用于图宿主和持久化，但不能替代核心判断。当前依赖里仍有 LangGraph，但生产 Owner 是 Custom Agent Kernel。

## Q5：Master Agent 如何选择工具

不是 Python 根据关键词映射工具。系统把 Tool Name、Description 和 Args Schema 放进 Prompt，LLM 根据当前 Goal、Coverage Gap、Open Question、Artifact Memory 和最近 Trace 返回 Tool Call。代码只负责校验 Tool 是否注册、参数是否满足 Schema、预算和权限是否允许。

## Q6：Tool Call 是模型原生 Function Calling 吗

当前主要是 Schema-driven Structured Decision。LLM 返回符合 Pydantic AgentDecision 的 JSON，里面包含 Tool Call，而不是强依赖某一家模型的原生 Function Calling。这样能兼容不同 OpenAI-compatible Endpoint。Tool Registry 再根据名字分发。

## Q7：为什么允许一次多个 Tool Call

用于紧密相关的短计划，减少不必要的 LLM Round Trip。Runtime 仍按顺序执行，每个 Observation 先更新 State，所以后一个工具可以看到前一个工具产生的状态。跨依赖很强或需要重新判断的动作仍应下一轮决定。

## Q8：Multi-Agent 是怎么做的

Master 可以按需委派 Vault Auditor、Researcher、Verifier 和 Knowledge Editor。任务有角色、Objective、Target Path 和 Question，最多四个独立任务并发执行。每个 Specialist 返回强类型 Finding、Tool Recommendation 或 Change Suggestion，并受角色 Tool Allowlist 限制。Specialist 不能直接 Apply 或写文件。

## Q9：每个 Specialist 都是完整 ReAct Agent 吗

不是。当前成熟度是动态委派、并发分析和 Typed Result，外部工具建议回到 Master Dispatcher。下一步才会给 Specialist 独立的多轮 Tool Loop 和 Per-task Budget。面试中应主动说明这个边界。

## Q10：State 里保存什么

包括 MetaContext、KnowledgeSchema、Entity/Claim/Relationship/OpenQuestion/SourceMemory、EvidenceRefs、TaskMemory、DecisionLog、ArtifactMemory、Vault/Health/Backlog、DelegationLog、AutonomyPolicy、BudgetUsage 和 HumanFeedback。State Version 当前为 3。

## Q11：如何控制 Prompt 长度

用 ContextPack 做有界筛选，只选择当前任务相关的 Active Claim、Evidence、Open Question 和 SourceMemory；排除 Hidden、Rejected、Superseded 和无关内容。Artifact 只给摘要和路径，不把整个 Vault 每轮塞进 Prompt。Recent Trace 只保留尾部十条。

## Q12：如何处理 LLM 输出不合法 JSON

Structured Parsing 失败后发起一次 JSON Repair，要求只输出符合 AgentDecision 的 JSON。Repair 仍失败时，不静默切回固定 Workflow，而是构造 `update_task_state` 记录错误，让循环保持可观察并在连续失败门限下停止。

## Q13：长文档为什么不用 Structured Output

控制面适合 JSON，长 Markdown 不适合。项目曾因强迫 Writer 输出 JSON 导致 JSONDecodeError 和模板兜底。当前 Decision/Specialist 用 Structured Completion，Artifact Writing 用 Plain Text Completion，并按 Section 写作和发 Heartbeat。

## Q14：怎么避免写作失败后生成垃圾文件

Writer 有可用性检查，正文长度、Heading 等不满足就不保存 Artifact。失败会记录 Observation 和 Failed Writes；可选卡失败可以 Partial Success，主写作连续失败会停止。没有真实 Artifact 就不能 Completed。

## Q15：如何判断资料够不够写

`evaluate_coverage` 综合 Evidence Count、Claim Count、Verified/Partial Ratio、Source Count、Open Question Penalty 和 Completion Criteria，输出 Score、Status 和 Ready to Write。数字是工程辅助，不是唯一标准，Master 还会结合用户目标和来源策略决定是否继续研究或先写带待验证项的初版。

## Q16：RAG 是怎么做的

统一 ProjectRetriever 同时跑 Lexical 和 Vector。Lexical 来自 SQLite FTS 和词项匹配；Vector 使用本地 FastEmbed `BAAI/bge-small-zh-v1.5`，索引 Evidence、Document Segment 和 Active Artifact。两路候选用 RRF 融合，Citation 返回两路 Rank、Score、Model、Path、Hash 和 Verification Status。

## Q17：为什么 RRF，不直接加 BM25 和 Cosine 分数

两种分数量纲不同，直接加权很难稳定。RRF 只依赖名次，能够融合精确关键词和语义召回，也更容易解释和测试。

## Q18：向量索引如何增量更新

Chunk 保存 Content Hash、Provider 和 Model。Hash 不变不重新 Embedding；只改 Metadata 就复用 Vector；内容变化重新生成；Source 删除或 Artifact Supersede 时删除 Stale Chunk。Force Rebuild 在一个 Transaction 中发布，失败保留旧 Snapshot。

## Q19：模型不可用怎么办

如果用户主动禁用 Embedding，状态是 Lexical；如果配置了语义检索但模型加载或查询失败，状态是 Lexical Degraded。系统继续返回 Lexical 结果，但前端明确显示降级，不能把关键词结果说成 Hybrid。

## Q20：为什么用 SQLite，不用 pgvector

当前是单用户/私有化 Local-first 产品，SQLite 能提供 Transaction、FTS5、Blob 向量和简单备份，部署更轻。主要延迟来自 LLM/Search，不是数据库并发。多租户和高并发时才迁移 PostgreSQL/pgvector。

## Q21：搜索如何接多个 Provider

通过 SearchProvider 接口适配 Tavily、Serper、Brave、Exa 和 Firecrawl。Multi 模式并发调用、隔离单 Provider 失败、Canonical URL 去重，并 Round-robin 合并，避免一个 Provider 垄断 Top N。

## Q22：怎么控制搜索费用

分别计数 Search Tool Call、实际 Provider Request、正文 Extraction 和 Writer Call。Multi Fan-out 按真实请求数扣预算，同 Run Resume 不重置。还有 Iteration、文件数和 Changed Bytes 限额。

## Q23：如何保证搜索只访问允许网站

Project 保存 Source Pack、Allowed/Blocked Domains 和 Prefer/Require。Require 是硬白名单，LLM 只能缩小。Provider 返回结果后，后端重新检查 Canonical Host；越界 URL 不创建 Evidence。

## Q24：网页抽取如何防 SSRF

只允许 Public HTTP/HTTPS，拒绝 Credentials、Localhost、Private/Reserved/Loopback/Link-local IP。DNS 解析后检查所有地址，本地 HTTP Extractor 对每次 Redirect Target 重新校验。

## Q25：怎么防止 Agent 编造引用

Evidence ID 必须在当前 Project 数据库中真实存在。Reducer、Artifact Review 和 ChangeSet Apply 都做解析；Unknown 或 Cross-project ID 失败。Verified Claim 没有真实 Evidence 会降级。当前仍需加强 Claim 文本与 Evidence 正文的语义支持校验。

## Q26：如何处理证据冲突

数据模型保留 Conflicting/Corroborating IDs、Claim Conflicts、Needs Counterevidence，并可委派 Verifier。不能解决时保留双方和未决状态，不删除历史。当前完整 NLI/Claim-level 裁决仍是下一阶段。

## Q27：为什么修改知识要 ChangeSet

已有知识是长期资产，不能让 LLM 直接覆盖。ChangeSet 带 Before/After、Unified Diff、Base Hash、Evidence 和 Operation。审批后 Apply，Hash 不一致就 Conflict。整个 Journal 先预验证，避免部分写入。

## Q28：回滚怎么实现

Artifact Revision 不可变。Update Rollback 创建一个内容等于 Before Content 的新 Revision，保留时间线；Create Rollback 将新 Artifact 设为 Inactive。ChangeSet 记录 Rollback Artifact IDs 和时间。

## Q29：如何恢复中断任务

每个 Artifact 写入后保存 State Checkpoint。人工等待使用同 Run Resume，反馈进入 State 且预算不重置；Worker 崩溃使用 Lease Reconciliation，带 Checkpoint 的 Run 标 Interrupted，再创建唯一 Recovery Child。无 Checkpoint 的 Run 明确失败。

## Q30：SSE 为什么需要 Heartbeat

LLM 和长写作可能几十秒无输出。Heartbeat 告诉用户系统仍在决策，也续 Run Lease。前端显示真实 Timeline，刷新后从 Snapshot 和持久 Event 恢复。

## Q31：如何避免一个 Run 重复执行

创建 Run 前 Reconcile Stale Lease 并检查 Active Run；Waiting Resume 用 Compare-and-Set；Recovery Child 有唯一索引；Event Append 和 Finalize 校验 Lease Owner 和 Expiry。

## Q32：最大的技术难点是什么

不是接 LLM API，而是把自主决策和工程控制同时做好：State 结构、工具权限、预算、证据、持久化、长任务可观察、人工恢复、版本冲突和真实产物验收。其中从固定 Workflow 切到唯一 Agent Kernel Owner 是最关键的架构重构。

## Q33：项目做过哪些真实验收

真实配置 `deepseek-v4-flash + Tavily + HTTP Extraction` 跑通过 V3：42 条 Search Evidence、4 个 Active Artifact、Approve/Apply/Same Run Resume/Completed、完整 `.sectorbreaker` 导出，耗时约十分钟。另有真实 Vault Import -> Audit -> ChangeSet -> Apply -> Restart -> Rollback -> Re-export 验收。

## Q34：已经上线了吗

已经上线，后端运行在阿里云服务器。Local-first 指知识和索引可以在私有环境内运行，不是只能本机访问。当前更准确的产品形态是单用户/私有化工作台，而不是多租户公有 SaaS。

## Q35：上线后如何保证数据安全

知识原文、SQLite、向量索引和模型缓存在服务端私有目录；API Key 不下发前端，配置写入原子替换并保留备份；外部 URL 有 SSRF 防护；来源策略和写入权限由代码硬执行；已有知识更新要审批和 Base Hash。

## Q36：如果要扩展到高并发怎么做

把 SQLite 迁移到 RDS PostgreSQL，向量迁移 pgvector/Vector DB，Run 执行拆到 Queue Worker，Lease 放到共享存储，上传/导出放 OSS，加入租户隔离、认证、Rate Limit、Monitoring 和 Cost Accounting。当前不提前实现，因为不符合现阶段业务负载。

## Q37：你的个人贡献是什么

可以回答：我负责 Agent Kernel 核心架构、State/Tool/Observation/Reducer 契约、Specialist 角色边界、Provider 接口、本地 Hybrid RAG、知识版本和 ChangeSet 控制面、Run Resume/Recovery、SSE 可观察性，以及真实验收和版本隔离治理。根据实际参与情况删减，不要把团队成员完成的部分全部归到自己。

## Q38：下一步最重要的优化是什么

1. Claim-level Citation Support 和反证门禁；
2. Specialist 独立预算工具循环；
3. Agent/RAG 标注评测集；
4. 真实垂直站点 Connector；
5. 受控 Site Crawl；
6. Scheduled Maintenance；
7. 多用户和云端规模化能力。
