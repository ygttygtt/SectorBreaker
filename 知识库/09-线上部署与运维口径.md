# 线上部署与运维口径

## 先统一事实

- SectorBreaker 不是只在开发机运行的 Demo，而是已经上线的产品。
- 后端统一部署在阿里云服务器。
- 当前代码库没有公开完整生产部署脚本，因此不能擅自声称具体 ECS 规格、Kubernetes、Nginx、云数据库、QPS 或 SLA。
- “Local-first”不等于“只能 localhost”。它表示知识数据、索引和模型可以在私有运行环境中落地，产品不强制把用户 Vault 托管到第三方云知识库。

## 可讲的线上拓扑

```text
用户浏览器
  -> 线上访问入口
  -> React/TypeScript 前端
  -> FastAPI 后端（阿里云服务器）
       |-- Agent Kernel / SSE
       |-- SQLite 控制面与向量索引
       |-- Managed Export / Model Cache / Runtime Config
       `-- 外部 LLM/Search/Extraction Provider
```

如果面试官追问反向代理、HTTPS、进程管理、容器编排，请按真实线上环境回答。当前知识库不替你虚构没有提供的品牌和参数。

## 为什么线上还使用 SQLite

当前产品是单用户或私有化知识工作台，主要压力来自长耗时 Agent IO、LLM/Search API 和本地 Embedding，不是高并发 OLTP。SQLite 的优势：

- 一个文件即可保存项目控制面；
- FTS5、Transaction 和 Blob 足够支撑当前需求；
- 备份和迁移简单；
- 适合私有部署和离线使用；
- 不需要额外运维 PostgreSQL/Vector Database。

上线不等于必须用分布式数据库。架构选择要匹配业务并发模型。

## 生产持久化目录

线上环境至少需要持久保存：

- SQLite Database；
- Exported Vault；
- Runtime Provider Config；
- FastEmbed Model Cache；
- 用户上传资料；
- 必要日志和备份。

这些数据不能放在随容器或临时进程销毁的文件系统中。若实际部署使用容器，需要把这些目录挂载到持久卷。

## 配置与密钥

后端支持 OpenAI-compatible LLM、多个 Search Provider 和 Extraction Provider。密钥保存在服务端 Runtime Config，不下发给前端。

当前安全处理：

- 状态 API 只返回哪些 Provider 已配置，不返回 Secret；
- 空白 Secret 字段不会覆盖已存 Key；
- Runtime Config 采用临时文件 + Atomic Replace；
- 保留一个可恢复 Backup；
- 平台允许时尽力设置 Owner-only 权限；
- Error Message 对疑似 Key 做 Redact。

## 运行可靠性

### Run Lease

每个 Worker 有 Lease Owner 和 Expiry。只有当前 Owner 能续 Heartbeat、追加 Event 和 Finalize，避免旧进程和新进程同时操作。

### Checkpoint

Artifact 写入后即时 Checkpoint，服务重启后可以从 Durable State 恢复。

### Stale Run Reconciliation

启动或创建新 Run 时检查过期 Lease：有 Checkpoint -> Interrupted，可恢复；无 Checkpoint -> Failed，不制造假恢复。

### Partial Success

可选解释卡失败不会丢掉已经完成的主文档；主写作连续失败会停止。只要没有真实 Artifact，就不能标 Completed。

## 线上网络安全

- `user_materials_only` 硬阻断联网；
- Source Policy 和 Domain Allow/Block 在代码中执行；
- 搜索结果做后置 Host 校验；
- 正文抽取拒绝私网、Localhost、保留地址和带 Credential URL；
- Local HTTP Redirect 每跳重新校验；
- Provider 调用有硬预算，防止异常 Fan-out。

## 可观测性

现有可观测面：

- Run Event Timeline；
- Thought/Action/Observation/State Update；
- Provider Outcome 和 Latency；
- Search/Provider/Extraction/Writer Budget；
- Error Severity；
- Lease/Terminal Reason；
- Retrieval Mode、Model、Index Count 和 Last Error；
- Artifact/ChangeSet/Checkpoint 历史。

当前尚未公开实现完整的 Prometheus/Grafana、分布式 Trace 或集中式日志平台，因此不要主动声称。

## 扩展性路线

当产品从单用户私有部署演进为多用户 SaaS，需要重新设计：

- 身份认证和租户隔离；
- PostgreSQL/RDS 和连接池；
- Object Storage；
- Background Queue / Scheduler；
- 分布式 Lease；
- Vector Store 或 pgvector；
- Rate Limit、Billing、Audit Permission；
- 监控告警和灾备。

这些属于下一阶段，不应包装成当前已完成。

## 面试回答：本地优先为什么还部署到云上

> Local-first 是数据和部署架构，不是访问地址。SectorBreaker 的知识库、SQLite、向量索引和模型缓存都可以留在用户私有环境，因此适合本机、局域网或单租户服务器部署。我们实际产品已经上线，后端运行在阿里云服务器，但仍保持单用户/私有化的数据边界。这样既可以远程访问，也不会强制把知识资产交给公共 SaaS 托管。

## 面试回答：为什么没有直接上微服务

> 当前瓶颈主要是 LLM、搜索和正文抽取的长 IO，以及单用户知识管理，不是服务内部的高并发。先用模块化单体把 Provider、Agent、Retrieval、Control Plane 的接口边界做清楚，部署和调试成本更低。等多租户、调度和吞吐成为真实问题，再拆 Worker、Vector Service 和 Storage，比一开始为了架构形式引入分布式复杂度更合理。
