# 证据系统、信源治理与安全

## Evidence 为什么是独立实体

如果只把 URL 写在 Markdown 尾部，会丢失很多决策所需信息。SectorBreaker 的 EvidenceItem 保存：

- Source Title、URL、Type、Channel、Policy；
- Search Snippet、Raw Excerpt、Summary；
- Extraction Provider、Metadata、Time；
- Source Quality、Claim Strength、Bias Risk、Recency；
- Verification Status；
- Corroborating/Conflicting Evidence IDs；
- Needs Counterevidence；
- Collected By 和 Used By Artifact IDs；
- Confidence 和 Collection Metadata。

这样 Agent 不只知道“搜到了网页”，还知道“怎么找到、是否抽正文、来源质量如何、是否需要反证、被哪些 Artifact 使用”。

## 搜索、正文抽取和事实验证是三件事

### SearchProvider

负责发现候选 URL，不证明网页正文是什么，也不证明 Claim 正确。

### ContentExtractionProvider

负责从已经发现的 Public URL 抽取可读正文。当前可选：

- Local HTTP Extraction；
- Firecrawl Scrape；
- Jina Reader。

### SourceVerificationProvider

负责评估来源类型和质量，例如 Official、Government、Company Disclosure、Media、Community，以及是否存在营销信号。

来源质量不等于事实已验证。启发式 Provider 最高只推荐 `partially_verified`，不能因为域名看起来权威就把 Claim 标成 Verified。

## Search Provider 适配

当前实现：

- Tavily；
- Serper；
- Brave Search；
- Exa；
- Firecrawl Search；
- MultiSearchProvider。

API、Agent 和 Specialist 不直接依赖厂商 SDK，只依赖 `SearchProvider.search(SearchQuery)` 接口。

## Multi Search 的并发和公平合并

MultiSearchProvider：

1. 按剩余 Provider Request Budget 选择可执行 Provider；
2. 使用 `asyncio.gather` 并发请求；
3. 单 Provider 失败不会抹掉其他结果；
4. URL Canonicalize 后去重；
5. Round-robin 合并不同 Provider 结果，避免第一个高产 Provider 占满 Top N；
6. 返回每个 Provider 的 Outcome。

Provider Outcome 包含：

```text
provider_id
status: ok | empty | timeout | error | skipped_budget
latency_ms
result_count
safe error code/message
```

## 预算为什么按真实 Provider Fan-out 计费

一次 `search_web` 在 Multi 模式下可能同时请求 5 个 Provider。如果只扣一次 Search Tool Call，就会低估成本和限额。

因此系统分别记录：

- Search Tool Calls；
- Actual Provider Requests；
- Extraction Requests；
- Writer Calls。

聚合 Provider 异常时会保守扣除已预留请求额度，避免通过异常路径绕过预算。

## Source Policy

Project Source Policy：

- `open_web`：允许开放网页；
- `reliable_first`：优先可靠站点；
- `reliable_only`：只接受可靠域；
- `user_materials_only`：硬阻断联网。

Project Source Preferences：

- Source Pack IDs；
- Custom Allowed Domains；
- Blocked Domains；
- `prefer` 或 `require`。

### Prefer

先查专用域；结果不足时允许一次显式 Fallback 到基础来源策略，并在 Observation 和 Evidence Collection Metadata 中记录。

### Require

专用域是硬白名单。LLM 提交的 Preferred Domains 只能缩小，不得扩张。没有匹配域的返回 URL 会被丢弃。

## 为什么还要做结果后置域名校验

搜索厂商的 Allowed Domain 参数可能只是 Hint，厂商也可能返回重定向或不符合策略的 URL。SectorBreaker 对每个结果重新解析 Canonical Host，执行 Allowed/Blocked 校验。

这属于“Policy Enforcement in Code”，不能只写在 Prompt 中。

## 正文抽取策略

一次 `search_web` 最多对前三个采纳 URL 执行正文抽取。原因：

- 控制延迟和费用；
- 避免一次搜索抓取大量页面；
- 先让 Agent 用少量高价值正文更新 State，再决定是否继续搜。

每条抽取独立失败：一个页面超时或不可读，不会让整个搜索结果回退。可读正文至少 80 字符，二进制、空内容或 PDF Header 会被拒绝为正文。

## SSRF 防护

Content Extraction 前执行 Public URL 校验：

- 只允许 HTTP/HTTPS；
- 禁止 URL 内嵌 Username/Password；
- 禁止 localhost；
- DNS 解析后拒绝 Loopback、Private、Link-local、Reserved、Multicast、Unspecified 地址；
- Local HTTP Extractor 对每次 Redirect Target 重新校验。

这个校验是基线 SSRF Gate，不代表系统有权访问登录态网页、内网站点或政策禁止的内容。

## Evidence Fail-closed

ChangeSet Apply 和 Artifact Review 都按 Project 查询 Evidence ID：

- 随便写一个 `EV-xxx` 字符串不能通过；
- 其他 Project 的 Evidence 不能跨项目使用；
- Factual Change 没有 Evidence ID 会 Denied；
- Verified Claim 的 Evidence 不存在会自动降级；
- Follow-up Artifact 只持久化真实 Evidence ID，普通 Retrieval Source ID 只作为上下文。

## 冲突和反证

数据模型已支持：

- Claim.conflicts_with；
- Evidence.conflicting_evidence_ids；
- Evidence.corroborating_evidence_ids；
- needs_counterevidence；
- Verifier Specialist；
- VerificationTask/Counterevidence Provider Boundary。

当前不足：还没有完整的 Claim-level NLI/Entailment Gate，无法自动证明每一句 Claim 被哪段 Evidence 语义支持，也没有形成统一的多来源裁决分数。

合理的下一步：

1. 把 Claim 拆成 Subject/Predicate/Object/Time/Scope；
2. 对 Claim-Evidence 做 Support/Contradict/Unrelated 分类；
3. 结合来源原始性、质量、时效和多源一致性评分；
4. 冲突无法消解时保留双方并请求人工，而不是删除不利证据。

## 面试回答：如何防止 Agent 编造引用

> 我们把引用门禁放在写入边界，而不是只靠 Prompt。Evidence 是数据库中的项目级实体，ChangeSet Apply、Artifact Review 和 Claim Reducer 都会解析引用 ID 并检查它是否真实存在、是否属于当前 Project。未知或跨项目 ID 不能通过，Verified Claim 会被降级。当前已经解决了 ID 真实性和项目归属，下一步还要加强 Claim 与 Evidence 正文之间的语义支持校验。
